# Schema Review

## Overall readiness

The schema set covers the main MVP concepts and already reflects many decisions that appear later in `docs/concepts/REQUIREMENTS.md`, including required conversation titles and descriptions, verified human email authentication, custom emoji assets, message hiding during moderation review, thread pausing, required moderation discussion conversations, and archival state. The object boundaries are generally understandable and the retained-history approach is consistent with DynamoDB remaining a later implementation choice.

The set is not ready to implement without a small integrity pass. The most important gaps are: confidential moderation discussions currently use the same tag-join model as ordinary conversations; `docs/schemas/note.yaml` permits audiences that contradict the context-specific visibility rules; `docs/schemas/moderation-action.yaml` does not connect each action type to the required target; and role-period ending events cannot be recorded reliably. Several other lifecycle records allow contradictory combinations such as an active credential with revocation fields or an active membership with an end reason.

In this report, a **foreign key** means an identifier that points to a record in another schema, such as `ModerationTicket.messageId` pointing to `Message.id`. An **enum** is a field restricted to a fixed list of values. A **lifecycle state** is a named stage such as `active`, `archived`, or `closed`. **Cardinality** means how many related records are allowed, such as one to ten active tags per conversation. A **derived field or rule** is a value or behavior calculated from other records rather than stored directly. **Normalization** means storing one concept once and referring to it by identifier rather than copying it into multiple records.

## Overkill or simplification candidates

### OS-01 — Optional reviewer assignment before assignment behavior exists

- **Affected schema item:** `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, field `assignedReviewerId`.
- **Current state:** The optional field stores one owner or administrator as the current reviewer, while its description and `ModerationTicket.status` explicitly say assignment rules remain undefined. No other listed schema depends on `assignedReviewerId`; `ModerationAction.actorIdentityId`, notes, and ticket timestamps still identify who actually worked on a report.
- **Requirement context:** The requirements say owners and administrators can access and review tickets, but explicitly leave reviewer-assignment rules and notifications undefined.
- **Why it matters:** Persisting a single assignee before deciding whether tickets can have no assignee, one assignee, several reviewers, reassignment history, or queues creates an accidental product rule and may require migration later.
- **Recommended action:** Remove `assignedReviewerId` for the MVP until assignment behavior is decided. This does not break a stated requirement because ticket access is role-based and no assignment workflow is required. If the field is retained only as forward-compatible storage, label it speculative in the dictionary and do not use it for authorization.

### OS-02 — Required token lookup prefix fixes an unresolved credential design

- **Affected schema item:** `docs/schemas/bot-credential.yaml`, object `Bot Credential`, required field `tokenPrefix`.
- **Current state:** Every credential must store both `tokenHash` and a non-secret lookup prefix. No other schema depends on the prefix; identities and authentication relationships use `BotCredential.identityId`.
- **Requirement context:** Bots must authenticate using tokens, but the requirements leave the data-access design and DynamoDB access patterns to implementation. Securely retaining a one-way `tokenHash` supports the requirement; a prefix is one possible lookup technique rather than product data.
- **Why it matters:** Requiring a prefix commits the framework-neutral model to a token format and lookup strategy before those choices have been made.
- **Recommended action:** Make `tokenPrefix` optional or remove it from the implementation-neutral schema. This does not remove token authentication or raw-token protection. Add it later if the selected credential format needs indexed prefix lookup.

### OS-03 — Broad audit payload can duplicate authoritative state

- **Affected schema item:** `docs/schemas/audit-event.yaml`, object `Audit Event`, field `details`.
- **Current state:** `details` accepts any object with arbitrary properties. Temporal tag and role records, `ModerationAction`, `Message` deletion fields, `Note` deletion fields, and `PostingSuspension` already hold authoritative history. No listed schema reads `AuditEvent.details` as a required relationship.
- **Requirement context:** History must be retained, but the requirements do not require complete snapshots or duplicated record bodies in audit events.
- **Why it matters:** Copying whole records into an unconstrained payload can create two disagreeing sources of truth, retain more profile or message content than necessary, and make audit consumers depend on undocumented shapes.
- **Recommended action:** Keep `Audit Event` because conversation-setting history is an unavoidable implication of retained conversation history, but narrow `details` to a small, non-authoritative explanation or before/after values for specifically documented actions. State that source schemas remain authoritative. This simplification preserves every stated history requirement.

## Risks and ambiguities for the next agent

### RA-01 — The requirements contain old "unresolved" text beside newer recorded answers

- **Affected schema items:** `docs/schemas/conversation.yaml` fields `matchingMode` and `status`; `docs/schemas/moderation-ticket.yaml` fields `status` and `discussionConversationId`; `docs/schemas/note.yaml` field `visibility`; and `docs/schemas/emoji.yaml` fields `type`, `scope`, and asset fields.
- **Current state:** The schemas generally follow the answers in Section 7: tickets have four statuses and a required discussion conversation; notes have context-specific audiences; custom emoji assets are represented; archived conversations are a lifecycle state. Earlier sections still say the ticket lifecycle, note visibility, emoji set, moderation-discussion requirement, archived-conversation behavior, and extra-tag search behavior are unresolved or optional.
- **Requirement context:** Section 7 contains direct answers that are more specific than those earlier statements, and the document changelog says recorded answers were reconciled.
- **Why it matters:** A developer reading only the earlier feature section may remove required fields or implement behavior that conflicts with the schemas, while a reviewer reading Section 7 will expect the newer decision.
- **Risk handling:** Treat the direct recorded answers as the current decisions for schema work, but flag the stale prose for later requirements reconciliation. Do not weaken schemas merely to match an earlier "unresolved" sentence.

### RA-02 — Reported-message resolution after review is not defined

- **Affected schema items:** `docs/schemas/message.yaml`, object `Message`, fields `status` and `hiddenByTicketId`; `docs/schemas/message-thread.yaml`, object `Message Thread`, fields `status` and `pausedByTicketId`; and `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, field `status`.
- **Current state:** A report can put a message in `hiddenPendingReview` and its thread in `paused`, and a ticket can advance to `reviewed` or `closed`. Nothing requires the message to become `visible` or `deleted`, or the thread to resume, when review ends.
- **Requirement context:** The requirements explicitly say to hide the reported message and pause its thread while it is reviewed. They permit reviewers to delete the message, but they do not state the outcome when the report is rejected or closed without deletion.
- **Why it matters:** A closed ticket can leave content hidden and a thread paused forever, or application components can implement different automatic outcomes.
- **Risk handling:** Do not invent a resolution enum in this pass. Record a product decision about the non-deletion outcome and its timing before adding ticket-to-message/thread transition constraints. Until then, application code must not assume `closed` alone means restore or delete.

### RA-03 — Tag component maximum length has no number

- **Affected schema item:** `docs/schemas/tag.yaml`, object `Tag`, field `value`.
- **Current state:** The regular-expression pattern correctly allows lowercase Latin letters, numbers, internal hyphens, and at most one colon, but it has no `maxLength` and no per-component length constraint.
- **Requirement context:** The tag rules say each component may contain hyphens "within the component's maximum length," but the requirements never give that maximum.
- **Why it matters:** Clients and APIs cannot enforce the same boundary, and an unbounded tag may create poor search, display, or DynamoDB key behavior.
- **Risk handling:** Ask for the maximum length of a simple tag and of each key/value component. Do not choose an arbitrary number based on database design.

### RA-04 — Canonical human email can disagree across two records

- **Affected schema items:** `docs/schemas/identity.yaml`, object `Identity`, fields `email` and `emailVerified`; `docs/schemas/human-authentication.yaml`, object `Human Authentication`, fields `identityId`, `email`, and `emailVerified`.
- **Current state:** Both records require a verified email for a human, but neither schema nor the dictionary says whether `Identity.email` must equal every authentication email, equal at least one, or represent a separately selected canonical address.
- **Requirement context:** Every human authentication must resolve to a positively identified email, and the data-model section says a human identity stores an email. Multiple OIDC or passwordless connections are not prohibited.
- **Why it matters:** Account linking, profile display, moderation lookup, and authorization could use different addresses for the same person.
- **Risk handling:** Define `Identity.email` as the canonical verified profile address and document whether it must match at least one active `HumanAuthentication.email`, or remove the duplicate only if the requirements are first changed. Do not silently assume all providers return the same email.

### RA-05 — Cross-record time ordering remains an application responsibility

- **Affected schema items:** `docs/schemas/conversation-tag.yaml` fields `effectiveFrom` and `effectiveTo`; `docs/schemas/membership-role-period.yaml` fields `effectiveFrom` and `effectiveTo`; `docs/schemas/posting-suspension.yaml` fields `startsAt`, `endsAt`, and `liftedAt`; and all lifecycle `createdAt`/`updatedAt` pairs.
- **Current state:** Each field has a date-time format, but standalone JSON Schema cannot compare two date-time values. It therefore permits an end before a start or an update before creation.
- **Requirement context:** These records implement temporal history, meaning history based on effective start and end times, and suspensions must remain active only until a specified end time.
- **Why it matters:** Reversed dates can make expired restrictions appear active, produce overlapping role periods, or corrupt historical ordering.
- **Risk handling:** Add explicit ordering rules to the dictionary and enforce them in the framework-neutral API/data package: end times must be later than start times, `liftedAt` must fall within the suspension interval, and update times cannot precede creation. This is not a request for a database-specific design.

### RA-06 — Multiple reports of the same message are not specified

- **Affected schema items:** `docs/schemas/message.yaml` field `hiddenByTicketId`, `docs/schemas/message-thread.yaml` field `pausedByTicketId`, and `docs/schemas/moderation-ticket.yaml` field `messageId`.
- **Current state:** Many tickets may reference the same message, but the message and thread can point to only one ticket currently responsible for hiding or pausing them.
- **Requirement context:** Any participant can flag a message, but the requirements do not say whether later flags create another ticket, join an existing open ticket, or are rejected while review is active.
- **Why it matters:** A second ticket can overwrite the first ticket link, and closing one ticket can restore content while another review is still active.
- **Risk handling:** Decide the cardinality for open tickets per message before changing the schemas. If one open ticket is allowed, document and enforce uniqueness. If several are allowed, derive hiding and pausing from the set of open tickets rather than one `hiddenByTicketId` or `pausedByTicketId`.
