# Schema Review

## Overall readiness

The schema set covers every durable concept explicitly named in `docs/concepts/REQUIREMENTS.md`: identities and bot credentials, conversations and tags, retained membership history, messages and emoji reactions, moderation tickets and actions, posting suspensions, and notes. The schemas are a strong POC starting point because identifiers, timestamps, soft-deletion fields, and the main per-record lifecycle rules are present.

The largest remaining risks are rules that span multiple records. JSON Schema validates one record at a time, so it cannot by itself guarantee one-to-ten active tags, preserve a final owner, verify that a reported message belongs to the stated conversation, or ensure that an actor is an authorized member. Those rules need to be stated as application and DynamoDB transaction invariants in `docs/schemas/DICTIONARY.md`. Several per-record combinations also currently permit contradictory data, particularly archived conversations without archive audit data, former memberships with a current active role, removed records without the actor who removed them, and posting suspensions whose status disagrees with their timestamps.

Terminology used below: an **enum** is a fixed list of allowed values; a **lifecycle state** is a status value showing which phase a record is in; a **foreign key** is an identifier field that points to another record; **cardinality** is the allowed number of related records; a **derived field** is a stored value that can instead be calculated from other fields; and **normalization** means storing one canonical representation, such as lowercase tag text, for reliable comparison.

Severity reflects likely POC impact: **high** can break access control, privacy, or a core flow; **medium** can produce incorrect history or ambiguous application behavior; **low** is primarily maintainability or audit clarity.

## Overkill or simplification candidates

These items are candidates, not automatic deletions. Agent 2 should simplify only where the existing requirements and relationships still work after the change.

### `docs/schemas/tag.yaml`, object `Tag`, field `kind`

- **Affected schema item:** `Tag.kind` currently stores `simple` or `keyValue`, while `Tag.normalizedValue` already reveals whether the value contains a colon.
- **Current dependencies:** The field is required by `tag.yaml`; no entry in `docs/schemas/DICTIONARY.md` describes a workflow, permission check, report, or relationship that depends on `kind` independently of `normalizedValue`.
- **Requirement context:** The requirements distinguish a simple value from a key/value example but require only a normalized, case-insensitive tag value as durable data. They do not require storing a separate classification.
- **Why simplification is safe:** Removing `kind` would not remove tag text, search behavior, sharing, casing normalization, or conversation associations. It would remove a value that can drift from the colon structure in `normalizedValue`.
- **Recommended action:** Prefer removing `kind` and deriving the presentation distinction from `normalizedValue`. If Agent 2 keeps it for query access, add a conditional that makes it agree with the string and document why denormalizing—that is, intentionally storing the same fact twice—helps a concrete DynamoDB access pattern.

### `docs/schemas/posting-suspension.yaml`, object `Posting Suspension`, field `status`

- **Affected schema item:** `Posting Suspension.status` stores `active`, `lifted`, or `expired` in addition to `startsAt`, `endsAt`, and `liftedAt`.
- **Current dependencies:** The dictionary calls `status` the current operational state, but no requirement depends on the stored value rather than a calculation from timestamps. Permission checks already need the timestamps.
- **Requirement context:** The requirement is a bounded restriction with an end date or time and optional early restoration. It does not require a separately persisted status.
- **Why simplification is safe:** The application can derive whether a suspension is pending, active, lifted, or expired from the current time, interval, and `liftedAt`. Removing the field prevents a stale `active` value after `endsAt` and preserves every required historical fact.
- **Recommended action:** Consider removing `status` and documenting the derived-state calculation. If efficient DynamoDB querying requires a stored status, keep it but implement SR-12 and document which write updates it at expiration.

### `docs/schemas/message.yaml`, object `Message`, field `moderationTicketId`

- **Affected schema item:** `Message.moderationTicketId` stores the ticket directly responsible for deletion, while `Moderation Ticket.messageId` already points from every report to its message and `Moderation Action` can point to both the ticket and target message.
- **Current dependencies:** Only the `Message` field description and dictionary's moderation relationships depend on this shortcut. The source ticket and delete action remain reachable without it.
- **Requirement context:** A ticket must link to its reported message, and moderation actions must remain associated with the ticket. The requirements do not say a message stores one deletion ticket.
- **Why simplification is safe:** Removing the backward pointer does not lose the report, action, actor, or deleted message. It also avoids a misleading single-value field when multiple tickets report the same message.
- **Recommended action:** Consider removing `Message.moderationTicketId` and use `Moderation Action.moderationTicketId` plus `targetMessageId` as the deletion audit link. If retained for query performance, apply SR-08 and document that it identifies only the ticket that caused deletion, not every ticket for the message.

### `docs/schemas/membership-event.yaml` and `docs/schemas/moderation-action.yaml`, fields `updatedAt`

- **Affected schema item:** Both objects describe immutable-style audit entries but require `updatedAt`, which their descriptions say is normally equal to `createdAt`.
- **Current dependencies:** Each YAML file requires the field; no requirement or dictionary relationship needs audit events to be edited after creation.
- **Requirement context:** The requirements ask to retain membership and moderation history. An append-only record supports that history more clearly than a mutable timestamp.
- **Why simplification is safe:** Removing `updatedAt` retains the event occurrence time and creation time and reduces the chance that an audit record appears editable without a defined correction policy.
- **Recommended action:** Consider removing `updatedAt` from these two objects and describe them as append-only records. Keep it only if there is a defined correction workflow, which is currently not stated.

### `docs/schemas/identity.yaml`, object `Identity`, field `deletedAt`

- **Affected schema item:** `Identity.deletedAt` exists alongside `Identity.status`, whose `disabled` value already prevents authentication and use.
- **Current dependencies:** No stated identity deletion flow, dictionary relationship, or permission rule depends on distinguishing soft deletion from disabled status.
- **Requirement context:** Identity records must remain attributable so old messages and actions retain a visible author. The requirements do not ask users to delete identities.
- **Why simplification is safe:** Removing `deletedAt` preserves the stable identity, display name, and ability to disable access. It avoids an undefined combination such as `status: active` plus `deletedAt`.
- **Recommended action:** Consider removing `deletedAt` until an identity-deletion requirement exists. If retained, define and constrain how it relates to `status: disabled` without erasing historical attribution.

## Risks and ambiguities for Agent 2

### Tag grammar and casing are deliberately unresolved

- **Affected schema item:** `docs/schemas/tag.yaml`, object `Tag`, fields `normalizedValue`, `displayValue`, and their regular-expression `pattern` constraints.
- **Current state:** The patterns allow any number of nonconsecutive hyphen-separated segments and exactly zero or one colon. `normalizedValue` requires lowercase; `displayValue` permits preserved uppercase letters.
- **Requirement context:** The requirements forbid Unicode and whitespace, require case-insensitive comparison, and forbid a component from beginning or ending with a hyphen. They explicitly leave the number of hyphens, multiple-colon behavior, and display casing unresolved.
- **Why it matters:** Changing these patterns now would silently choose product behavior and could reject tags the final decision intends to permit. Existing stored values could later need migration.
- **Recommended action or question:** Do not broaden or narrow the patterns in this phase. Ask whether multiple separator hyphens and multiple colons are allowed and whether display casing is preserved; then update both patterns and descriptions together.

### Moderation ticket workflow values are provisional

- **Affected schema item:** `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, fields `status`, `assignedToIdentityId`, `resolvedAt`, `resolvedById`, and `resolutionSummary`.
- **Current state:** The enum allows `open`, `inReview`, `resolved`, and `closed`, but there are no conditional requirements connecting terminal states to resolution metadata and no defined distinction between `resolved` and `closed`.
- **Requirement context:** Tickets must be reviewable and retained, but exact statuses, assignment, notifications, and closure behavior are explicit open questions.
- **Why it matters:** Tightening conditional rules before the lifecycle is chosen could encode the wrong workflow; leaving the fields unconstrained can produce terminal tickets without an outcome.
- **Recommended action or question:** Leave the provisional values unchanged unless a product owner answers: “What is the difference between `resolved` and `closed`, and which status requires `resolvedAt`, `resolvedById`, and `resolutionSummary`?”

### Note visibility values are not yet authoritative

- **Affected schema item:** `docs/schemas/note.yaml`, object `Note`, field `visibility`.
- **Current state:** `visibility` is optional but, when supplied, must be `authorOnly`, `moderators`, `owners`, or `participants`. The schema does not say whether visibility may change after creation.
- **Requirement context:** People may add notes and moderators may attach operational notes, but the visibility model and mutability are explicitly unresolved.
- **Why it matters:** A default audience chosen implicitly by application code could expose personal or moderation notes to unintended readers.
- **Recommended action or question:** Do not make `visibility` required or choose a default in this phase. Ask which audiences are supported, what default applies to each note target, and whether the value may change after creation.

### Emoji uniqueness cannot be finalized yet

- **Affected schema item:** `docs/schemas/emoji-reaction.yaml`, object `Emoji Reaction`, relationship `(messageId, identityId, emoji)` and field `removedAt`.
- **Current state:** Multiple active reaction records with the same message, identity, and emoji are possible, as are multiple different emoji values from one identity.
- **Requirement context:** The emoji set and whether one identity may add multiple reactions to the same message are explicit open questions.
- **Why it matters:** A premature uniqueness rule could prevent required reactions; no rule could allow accidental duplicate counts in the UI.
- **Recommended action or question:** Apply only the authorization and relationship checks in SR-11. Ask whether one identity may have zero or one total reaction, one reaction per emoji, or multiple retained reactions per message before defining an active uniqueness key.

### Archived conversation behavior is unresolved beyond retention

- **Affected schema item:** `docs/schemas/conversation.yaml`, object `Conversation`, field `status`; relationships to `Message`, `Membership`, `Conversation Tag`, and search results.
- **Current state:** The schema records `active` or `archived` but does not define whether archived conversations are searchable, readable, writable, or joinable.
- **Requirement context:** Archival replaces deletion and retains data, while participant-view and search behavior after archival are explicit open questions.
- **Why it matters:** Separate client and API code paths could treat archived conversations differently, allowing new messages or hiding records unexpectedly.
- **Recommended action or question:** Implement only SR-04's metadata consistency. Ask whether archived conversations are excluded from search, readable by prior members, and read-only for all actors before adding any further lifecycle fields.

### A moderation discussion lacks a defined confidential join rule

- **Affected schema item:** `docs/schemas/conversation.yaml`, object `Conversation`, fields `purpose`, `visibility`, and `moderationTicketId`; `docs/schemas/membership.yaml`, moderation-discussion memberships.
- **Current state:** Even after SR-03 makes the conversation unlisted, the general unlisted flow lets any non-banned identity join after supplying all tags. No schema field limits membership to ticket reviewers.
- **Requirement context:** The discussion is called private or confidential, but it also behaves like a normal conversation; whether it is required or optional is unresolved, and no invitation or access-list model is defined.
- **Why it matters:** Unlisted discovery suppresses identity but is not equivalent to authorization. A user who guesses the complete tags could enter sensitive moderator discussion under the general join flow.
- **Recommended action or question:** Do not create a speculative access-control object. Ask: “May only owners and administrators of `Moderation Ticket.conversationId` join its `moderationDiscussion` conversation, and if so, should membership be created only by explicit moderator addition rather than tag matching?”

### Current-role handling for former memberships may affect DynamoDB queries

- **Affected schema item:** `docs/schemas/membership.yaml`, object `Membership`, fields `currentStatus` and `currentRole`.
- **Current state:** SR-05 recommends omitting `currentRole` for `left` and `removed` because role history lives in `Membership Role Period`; existing queries may instead expect a required scalar on every membership.
- **Requirement context:** Former members must remain visible to owners and administrators but have no participation rights; `none` is specifically the banned role.
- **Why it matters:** Using `none` for every inactive membership would blur a ban with a voluntary departure, while retaining the last privileged role can be unsafe if code checks role alone.
- **Recommended action or question:** Agent 2 should prefer SR-05 unless a concrete current-state query requires the last role. If such a need exists, rename the value to `lastRole`, keep authorization dependent on `currentStatus: active`, and leave `none` reserved for bans.

### Cross-record consistency must be implemented outside YAML validation

- **Affected schema item:** All identifier relationships described in `docs/schemas/DICTIONARY.md`, especially `Membership.identityId`, `Message.authorIdentityId`, `Moderation Ticket.messageId`, `Emoji Reaction.messageId`, and `Posting Suspension.membershipId`.
- **Current state:** Each identifier is a UUID string, but the YAML files do not and cannot prove that the referenced record exists or has matching conversation and identity values.
- **Requirement context:** Permissions, moderation routing, retained attribution, and private search behavior depend on those relationships being correct.
- **Why it matters:** Treating successful JSON Schema validation as complete validation could admit dangling or cross-conversation links and create security bugs.
- **Recommended action or question:** Update the relationship summary with the concrete invariants from SR-01, SR-02, and SR-06 through SR-13. State plainly that record validation and application-level relationship validation are separate checks; do not claim automated validation was run.
