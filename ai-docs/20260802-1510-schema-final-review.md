## Summary

The recorded answers require seven bounded adjustments to the current post-Agent-2 schema contract. The largest adjustment is moderation lifecycle handling: each report remains a distinct ticket with its own confidential discussion, a reviewer records whether that ticket keeps or removes the message, and message hiding or thread pausing must account for every unresolved ticket rather than one stored ticket identifier. The remaining changes add a warning action without inventing an unresolved reputation formula, make closed tickets terminal, set the tag-component limit to 15 characters, require an audit event for an author-controlled note-visibility change, and restrict conversation-scoped custom emoji creation to owners and administrators.

In this report, a **cross-record rule** is application behavior enforced by comparing separate records because one standalone JSON Schema document cannot express it. A **terminal state** is a lifecycle state that cannot transition to another state.

## Answered questions requiring no schema change

No answered question requires zero work across the complete schema contract. However, these parts of the recorded decisions are already represented and should not be redesigned:

- **SQ-02, distinct report discussions:** `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, already requires `discussionConversationId`. The `docs/schemas/DICTIONARY.md` cross-record rules already make that ID globally unique and require it to reference a separate confidential `Conversation` with `purpose: moderationDiscussion`, `accessMode: ticketReviewers`, and `visibility: unlisted`. FR-02 only adds the multiple-ticket aggregate lifecycle and explicit reporter-privacy rule.
- **SQ-06, storage mechanism for visibility history:** `docs/schemas/audit-event.yaml`, object `Audit Event`, already accepts `subjectType: note` and can carry a small before/after detail payload. FR-06 defines the missing product rule and stable event meaning without adding another schema object.
- **SQ-07, conversation custom-emoji record shape:** `docs/schemas/emoji.yaml`, object `Emoji`, already requires `ownerIdentityId` and `conversationId` for `type: custom`, `scope: conversation`. FR-07 adds only the missing role authorization rule.

## Non-actionable conflicts and risks

The items below are excluded from the recommendation count and are not additional questions.

### NR-01 — Karma, warning points, and reputation remain an implementation-unsafe choice

- **Affected schema item:** Potential new fields or objects related to `docs/schemas/identity.yaml`, object `Identity`, and warnings represented by `docs/schemas/moderation-action.yaml`, object `Moderation Action`.
- **Current state:** `Identity` has no karma, reputation, or warning-points field. `ModerationAction` can be conservatively extended with the warning record described by FR-03.
- **Requirement context:** SQ-01 clearly asks for a reviewer warning action, but the answer describes karma, warning points, and Stack Overflow-like reputation as possible ways to reflect the warning rather than selecting a scoring model.
- **Why it matters:** A stored score would require rules for initial value, increments or decrements, scope, decay, visibility, appeals, and whether false-report and harmful-post warnings carry equal weight. None of those decisions is recorded.
- **Risk disposition:** Implement only the durable `warnIdentity` action in FR-03. Do not add a reputation balance, points ledger, or derived score until a later product decision defines its meaning.

### NR-02 — SQ-05 does not select a safe canonical-email relationship

- **Affected schema item:** `docs/schemas/identity.yaml`, object `Identity`, fields `email` and `emailVerified`; `docs/schemas/human-authentication.yaml`, object `Human Authentication`, fields `identityId`, `email`, `issuer`, and `subject`; matching dictionary entries.
- **Current state:** A human `Identity` requires one verified `Identity.email`. Each linked `HumanAuthentication` also requires a verified email, and one identity can already own multiple authentication records. No cross-record rule says whether `Identity.email` must match all, one, or none of those sign-in addresses.
- **Requirement context:** SQ-05's answer anticipates additional account email addresses and possibly phone numbers, and says an OIDC email must resolve to the account's email data. It does not select whether `Identity.email` is canonical, which address is used for profile display, whether every added address must be verified, or whether a non-sign-in address may become canonical.
- **Why it matters:** Removing `Identity.email`, converting it to an array, or requiring it to match one authentication record would each create a different account-linking and recovery contract. Guessing could merge two users incorrectly or make a legitimate linked login unreachable.
- **Risk disposition:** Make no schema change from SQ-05 in this pass. Continue treating each `HumanAuthentication.email` as verified sign-in evidence and do not assume it equals `Identity.email`. The requirements reconciliation should record only the clear direction that an account may have multiple email-linked sign-in connections and that OIDC email participates in identity resolution, while preserving the unresolved canonical-address choice as a non-actionable risk.

### NR-03 — Existing requirements prose is stale relative to the recorded answers

- **Affected schema item:** `docs/concepts/REQUIREMENTS.md`, especially moderation ticket workflow, tag grammar, note visibility, and custom-emoji permission text.
- **Current state:** The requirements still describe ticket reopening, tag component length, post-creation note visibility, and custom-emoji permissions as unresolved. The exact answered questions report records newer decisions for those areas.
- **Requirement context:** The workflow treats substantive recorded answers as newer product decisions and reserves requirements edits for the later reconciliation phase.
- **Why it matters:** Leaving both statements in place after the workflow would make implementers choose between contradictory sources.
- **Risk disposition:** Agent 7 must reconcile the clear decisions after any approved final schema changes. This final-review phase does not edit `docs/concepts/REQUIREMENTS.md`.
