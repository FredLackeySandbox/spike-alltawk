# Schema Changes

## Source review

This improvement pass used `ai-docs/20260722-0719-schema-review.md`. It compared the schemas and dictionary with `docs/concepts/REQUIREMENTS.md`. This pass accepted all 14 numbered recommendations and all five simplification candidates. No recommendation was rejected, and no validator, linter, test suite, package script, dependency install, or other project tooling was run.

Terms used below: an **enum** is a fixed list of allowed values; a **lifecycle state** is a value that describes the current phase of a record; a **foreign key** is an identifier that points to another record; an **invariant** is a rule that must remain true after every successful write; a **transaction** is a group of writes that either all succeed or all fail; and a **derived field** is a value calculated from other stored data instead of being stored independently.

| SR-01 | `docs/schemas/conversation-tag.yaml`, object `Conversation Tag`, fields `conversationId`, `tagId`, `position`, and `removedAt`; `docs/schemas/DICTIONARY.md`, Conversation Tag invariants | Accepted | Before this change, `position` allowed 1 through 10 on one record but could not stop a conversation from having zero or more than ten active records or duplicate active tags and positions. The dictionary now requires 1–10 active records per `Conversation.id`, unique active `(conversationId, tagId)` and `(conversationId, position)` pairs, transactional creation of the conversation, first owner, and initial tags, and rejection of final-tag removal. This matters because discovery and unlisted joining operate on the complete active tag set. | Every conversation must have one to ten tags, including after tag management, and its creator must become the first owner. | JSON Schema still cannot enforce this cross-record cardinality—the allowed number of related records. | SR-02 | `docs/schemas/membership.yaml`, object `Membership`, fields `conversationId`, `currentStatus`, and `currentRole`; `docs/schemas/membership-role-period.yaml`, object `Membership Role Period`, fields `conversationId`, `role`, and `effectiveTo`; `docs/schemas/DICTIONARY.md`, Conversation ownership invariant | Accepted | Before this change, independent Membership and Membership Role Period records could leave an active conversation without an owner. The dictionary now requires any write ending an active owner membership or role period to prove that another active owner exists, unless the same transaction archives the Conversation. It also states that an administrator cannot create, end, or alter an owner role period. This preserves a clear actor who can manage tags, membership, moderation, and archival. | Every active conversation must have at least one owner; the last owner must transfer ownership before leaving or archive the conversation; administrators cannot alter owners. | The rule spans several records and remains an application transaction responsibility. A developer must not rely on validating only the changed Membership or Membership Role Period record. |
| SR-03 | `docs/schemas/conversation.yaml`, object `Conversation`, fields `purpose`, `moderationTicketId`, `visibility`, and `matchingMode`; `docs/schemas/DICTIONARY.md`, Conversation entry | Accepted | Before this change, `purpose: moderationDiscussion` required a ticket link but could still be listed publicly, and a standard conversation could carry `moderationTicketId`. The schema now requires a moderation discussion to use `visibility: unlisted`, `matchingMode: allTags`, and `moderationTicketId`; it prohibits `moderationTicketId` on a standard conversation. The dictionary explains that unlisted discovery does not itself authorize confidential access. | Ticket discussion is private or confidential, retains a relationship to its ticket, and otherwise uses the normal conversation model. Only listed conversations expose an identifiable search result. | The requirements do not define who may join a confidential moderation discussion. The schema prevents public listing but does not invent an invitation or access-control-list model. |
| SR-04 | `docs/schemas/conversation.yaml`, object `Conversation`, fields `status`, `archivedAt`, and `archivedById`; `docs/schemas/DICTIONARY.md`, Conversation entry | Accepted | Before this change, an archived Conversation could omit its archive time and actor, while an active Conversation could carry archive metadata. The schema now requires both `archivedAt` and `archivedById` for `status: archived` and prohibits both for `status: active`. This gives the UI and permission logic one internally consistent lifecycle state and preserves who performed the archival. | Archival is the owner-performed replacement for conversation deletion, and retained history is a POC success criterion. | Search, read, write, and join behavior for an archived Conversation remains an explicit product question, so no new archive-access fields or rules were added. |
| SR-05 | `docs/schemas/membership.yaml`, object `Membership`, fields `currentStatus` and `currentRole`; `docs/schemas/DICTIONARY.md`, Membership entry | Accepted | Before this change, `currentRole` was always required, so a `left` or `removed` Membership could still contain `owner`, `administrator`, or `member`. The schema now requires a non-`none` role only for `currentStatus: active`, requires `none` for `currentStatus: banned`, and prohibits `currentRole` for `left` and `removed`. The dictionary tells authorization code to require active status as well as an allowed role. Historical roles remain in Membership Role Period records. | Leaving or removal ends participation rights, while `none` specifically represents a ban and former members remain retained for history. | Existing application code may have assumed every Membership has `currentRole`. Developers must update such code to treat an omitted role on `left` and `removed` as intentional, not as corrupt data. |
| SR-06 | `docs/schemas/membership-role-period.yaml`, object `Membership Role Period`, fields `membershipId`, `conversationId`, `identityId`, `effectiveFrom`, and `effectiveTo`; `docs/schemas/DICTIONARY.md`, Role periods invariant | Accepted | Before this change, one-record validation could allow reversed intervals, multiple open periods, overlapping periods, or copied identity and conversation values that disagree with Membership. The dictionary now requires `effectiveTo` to be later than `effectiveFrom`, non-overlap, at most one open period per `membershipId`, matching copied identifiers, and an atomic end-current/create-next role change. These rules keep historical authorization and owner counts deterministic. | Membership roles must be stored over time with effective start and end timestamps, and the most recent valid role determines authority. | YAML cannot compare date-time values or inspect other periods. The application must enforce interval ordering, overlap prevention, and copied-identifier agreement on every role write. |
| SR-07 | `docs/schemas/conversation-tag.yaml`, object `Conversation Tag`, fields `removedAt` and `removedById`; `docs/schemas/DICTIONARY.md`, Conversation Tag entry | Accepted | Before this change, either removal field could appear alone. `dependentRequired` rules now make `removedAt` and `removedById` appear together. This means a removed assignment always records when removal occurred and which owner or administrator acted, while an active assignment contains neither removal field. | Owners and administrators manage tags, and conversation history must be retained rather than physically deleted. | The schema identifies the actor but cannot prove that `removedById` was an active owner or administrator at `removedAt`; authorization remains an application check. |
| SR-08 | `docs/schemas/message.yaml`, object `Message`, fields `deletedAt`, `deletedById`, and `deletionReason`; `docs/schemas/DICTIONARY.md`, Message entry and Message deletion invariant | Accepted | Before this change, a hidden message could omit its deletion actor, and a visible message could carry orphaned deletion metadata. The schema now requires `deletedById` with `deletedAt` and prohibits `deletedById` and `deletionReason` when `deletedAt` is absent. The dictionary requires the actor to be the author or an active owner or administrator at deletion time. `Message.moderationTicketId` was removed under SC-03, so ticket-driven deletion is represented by Moderation Action. | Authors may delete their own messages; owners and administrators may delete as moderation; deleted messages disappear from views but remain stored with moderation history. | Actor authorization and historical role lookup cross records. Application code must check the actor's relationship to the message and conversation at `deletedAt`. |
| SR-09 | `docs/schemas/moderation-action.yaml`, object `Moderation Action`, fields `type`, `targetIdentityId`, and `postingSuspensionId`; `docs/schemas/DICTIONARY.md`, Moderation actions and suspensions invariant | Accepted | Before this change, `suspendPosting` and `liftPostingSuspension` required a target identity but could omit the restriction record. Both action types now require `postingSuspensionId`. The dictionary requires the referenced Posting Suspension's `identityId` and `conversationId` to equal the action's target and conversation. This lets an audit reader identify the exact bounded restriction created or lifted. | Ticket reviewers may suspend posting until a specified time, and moderation actions must remain associated with the ticket and affected records. | YAML cannot confirm that the referenced Posting Suspension exists or matches the action. The application must enforce the documented foreign-key agreement. |
| SR-10 | `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, fields `ticketNumber`, `conversationId`, `messageId`, and `reportingIdentityId`; `docs/schemas/DICTIONARY.md`, Moderation tickets invariant | Accepted | Before this change, field descriptions stated the intended links but allowed a message from another conversation, an ineligible reporter, or a duplicate human-readable number. The dictionary now requires the message and ticket conversation to match, the reporter to have been an active member able to view the message at `reportedAt`, and `ticketNumber` to be globally unique through a DynamoDB conditional write or counter allocation. These checks prevent misrouting reports and ambiguous ticket numbers. | A flag must identify its message, source conversation, and reporting participant; owners and administrators of that conversation review it; ticket numbers are unique. | The allocation mechanism is intentionally not prescribed because the DynamoDB access layer is unresolved. Concurrent report creation must still use an atomic uniqueness mechanism. |
| SR-11 | `docs/schemas/emoji-reaction.yaml`, object `Emoji Reaction`, fields `messageId`, `conversationId`, and `identityId`; `docs/schemas/DICTIONARY.md`, Emoji reactions invariant | Accepted | Before this change, each identifier had the right format but could point to an unrelated message, conversation, or identity. The dictionary now requires the Message's `conversationId` to match the reaction and the reacting identity to have active membership at creation. This keeps conversation-scoped authorization and query results consistent. | Reactions are available only to active participants who can view the message and remain associated with the message and reacting identity. | The allowed number and kinds of reactions per identity remain unresolved. No uniqueness invariant for `(messageId, identityId, emoji)` was added. |
| SR-12 | `docs/schemas/posting-suspension.yaml`, object `Posting Suspension`, fields `membershipId`, `conversationId`, `identityId`, `startsAt`, `endsAt`, `liftedAt`, and `liftedById`; `docs/schemas/DICTIONARY.md`, Posting Suspension entry and Moderation actions and suspensions invariant | Accepted with simplification | Before this change, stored `status` could disagree with the time interval and lift fields, either field in a lift pair could appear alone, and copied identifiers could disagree with Membership. Under SC-02, `status` was removed. The schema now makes `liftedAt` and `liftedById` appear together. The dictionary requires `endsAt` later than `startsAt`, requires Membership identifiers to match, and defines operational state from the interval and early lift. This avoids a stale status while preserving every required restriction and audit fact. | Posting suspension is a bounded period that prevents one retained member from posting and must support an end date or time. | YAML cannot compare `startsAt` and `endsAt` or check Membership. Permission code must implement the documented derived-state calculation consistently. |
| SR-13 | `docs/schemas/bot-credential.yaml`, object `Bot Credential`, fields `identityId`, `status`, `expiresAt`, and `revokedAt`; `docs/schemas/DICTIONARY.md`, Bot Credential entry and Bot credentials invariant | Accepted | Before this change, a revoked credential could omit `revokedAt`, an active credential could include it, and the schema could not prove the identity was a bot. Conditional rules now require `revokedAt` for `status: revoked` and prohibit it for `status: active`. The dictionary requires `identityId` to reference `Identity.type: bot` and allows active authentication only before `expiresAt`, when present, and while `Identity.status` is active. | Bots authenticate with token credentials, and Bot Credential belongs to a bot Identity. Anonymous access is not permitted. | Identity type, identity status, and expiration evaluation are cross-record or time-dependent checks and remain application responsibilities. |
| SR-14 | `docs/schemas/membership-event.yaml`, object `Membership Event`, fields `type`, `fromRole`, and `toRole`; `docs/schemas/DICTIONARY.md`, Membership Event entry | Accepted | Before this change, transition events could omit the roles needed to explain what happened. The schema now requires both roles for `roleChanged`, requires `banned` to end at `none`, requires `unbanned` to start at `none` and end at a participating role, and requires `joined` and `rejoined` to have a non-`none` destination role. These conditions make retained membership history understandable. | History must retain joins, departures, removals, bans, restoration, and role changes; `none` is the banned role. | The schema does not define whether `left` or `removed` should include `fromRole`; requirements do not demand that field, and Membership Role Period retains the authoritative prior role. |
| SC-01 | `docs/schemas/tag.yaml`, object `Tag`, field `kind`; `docs/schemas/DICTIONARY.md`, Tag entry | Accepted | Before this change, required `kind` stored `simple` or `keyValue` even though the colon in `normalizedValue` already provides that distinction. `kind` was removed, and the dictionary now tells developers to derive the classification from `normalizedValue`. This prevents two stored representations of the same fact from disagreeing. | Requirements need a normalized, case-insensitive tag that may be simple or key/value, but they do not require a separate stored classification. | The exact tag grammar and display casing are still explicit product questions; no regular-expression pattern was broadened or narrowed. |
| SC-02 | `docs/schemas/posting-suspension.yaml`, object `Posting Suspension`, field `status`; `docs/schemas/DICTIONARY.md`, Posting Suspension entry | Accepted | Before this change, `status` duplicated state already represented by `startsAt`, `endsAt`, and `liftedAt`, and could remain `active` after the interval ended. `status` was removed. The dictionary now defines the state calculation from time and optional early lift. This prevents stale permission data while retaining the entire restriction history. | The requirement is a posting restriction with an end time, not a persisted status field. | If a future DynamoDB access pattern needs a queryable status, the team must define how expiration updates it before reintroducing the field. Until then, all permission paths must use the documented time calculation. |
| SC-03 | `docs/schemas/message.yaml`, object `Message`, field `moderationTicketId`; `docs/schemas/DICTIONARY.md`, Message entry | Accepted | Before this change, Message could store one deletion ticket even though multiple Moderation Tickets may report the same message. The field was removed. `Moderation Action.moderationTicketId` plus `Moderation Action.targetMessageId` now supplies the ticket-to-deletion audit link without implying that a message has only one report. | Tickets link to reported messages, and actions taken during review remain associated with the ticket. The requirements do not require a backward ticket pointer on Message. | Read paths that formerly expected a direct Message-to-ticket shortcut must query Moderation Actions or tickets instead. This may affect a future DynamoDB access pattern but avoids ambiguous data now. |
| SC-04 | `docs/schemas/membership-event.yaml`, object `Membership Event`, field `updatedAt`; `docs/schemas/moderation-action.yaml`, object `Moderation Action`, field `updatedAt`; `docs/schemas/DICTIONARY.md`, corresponding entries | Accepted | Before this change, both audit objects required `updatedAt` even though their descriptions said it normally equaled `createdAt` and no correction workflow existed. The two `updatedAt` properties were removed, and the dictionary describes both records as append-only. `occurredAt` preserves when the action took effect and `createdAt` preserves when the record was written. | Membership and moderation history must be retained; no requirement says these audit events can be edited after creation. | A future audit-correction workflow would need a separate correction event or an explicitly defined mutation policy. Developers should not mutate existing Membership Event or Moderation Action records silently. |
| SC-05 | `docs/schemas/identity.yaml`, object `Identity`, field `deletedAt`; `docs/schemas/DICTIONARY.md`, Identity entry | Accepted | Before this change, `deletedAt` existed beside `status: disabled`, but no requirement defined identity deletion or the relationship between those fields. `deletedAt` was removed. The dictionary explains that disabled status blocks access while the stable Identity remains for message and audit attribution. This avoids contradictory states such as active plus deleted. | Identities must remain visible with retained messages and actions; anonymous participation is prohibited; the requirements do not include an identity-deletion flow. | If identity deletion becomes a requirement, the team must define display-name retention, authentication behavior, and its relationship to disabled status before adding deletion metadata. |

Decision totals: **19 accepted**, **0 partial**, **0 rejected**. “Accepted with simplification” for SR-12 counts as accepted because removing the redundant `Posting Suspension.status` fully resolves the reported inconsistency while preserving the bounded restriction required by the product.

## Changed files

- `docs/schemas/DICTIONARY.md`: Updated the exact entries for Bot Credential, Conversation Tag, Conversation, Emoji Reaction, Identity, Membership Event, Membership Role Period, Membership, Message, Moderation Action, Posting Suspension, and Tag. Added application and DynamoDB transaction invariants for tag cardinality, final-owner protection, temporal role periods, deletion authorization, suspension links, ticket links and number uniqueness, reaction authorization, and bot credential eligibility. These changes document requirements that one-record YAML validation cannot enforce.
- `docs/schemas/conversation.yaml`, object `Conversation`: Added conditional rules for `purpose`, `moderationTicketId`, `visibility`, and `matchingMode` so a moderation discussion is linked and unlisted and a standard conversation has no ticket link. Added conditional rules pairing lifecycle state `status` with `archivedAt` and `archivedById` so archival has consistent retained audit metadata.
- `docs/schemas/conversation-tag.yaml`, object `Conversation Tag`: Added mutual dependencies between `removedAt` and `removedById` so retained tag-removal history always has a timestamp and actor.
- `docs/schemas/membership.yaml`, object `Membership`: Removed `currentRole` from the unconditional required list; required it for `currentStatus: active` and `banned`; prohibited it for `left` and `removed`. This separates present authorization from role history and reserves `none` for bans.
- `docs/schemas/message.yaml`, object `Message`: Required `deletedById` with `deletedAt`; prohibited `deletedById` and `deletionReason` without `deletedAt`; removed `moderationTicketId` so Moderation Action carries the ticket-to-deletion link without implying one report per message.
- `docs/schemas/moderation-action.yaml`, object `Moderation Action`: Required `postingSuspensionId` for `type: suspendPosting` and `liftPostingSuspension`; removed `updatedAt` so the audit record is append-only.
- `docs/schemas/posting-suspension.yaml`, object `Posting Suspension`: Removed derived field `status`; paired `liftedAt` and `liftedById`. The requirements-backed restriction remains defined by `startsAt`, `endsAt`, and any early lift.
- `docs/schemas/bot-credential.yaml`, object `Bot Credential`: Required `revokedAt` for `status: revoked` and prohibited it for `status: active`, aligning credential state with audit metadata.
- `docs/schemas/membership-event.yaml`, object `Membership Event`: Added role requirements for `roleChanged`, `banned`, `unbanned`, `joined`, and `rejoined`; removed `updatedAt` so retained history entries are append-only.
- `docs/schemas/tag.yaml`, object `Tag`: Removed redundant field `kind`; simple versus key/value presentation is derived from `normalizedValue`.
- `docs/schemas/identity.yaml`, object `Identity`: Removed undefined `deletedAt`; `status: disabled` remains the access-blocking state while historical attribution is retained.

No new schema file was added, and no existing schema file was renamed or removed. `docs/schemas/membership-role-period.yaml`, `docs/schemas/moderation-ticket.yaml`, and `docs/schemas/emoji-reaction.yaml` did not need one-record edits; their requirements-backed cross-record checks are documented in `docs/schemas/DICTIONARY.md`.

## Remaining known risks

- **Affected schema item:** `docs/schemas/tag.yaml`, object `Tag`, fields `normalizedValue` and `displayValue`. **Current state:** Their regular-expression patterns allow multiple nonconsecutive hyphens but exactly zero or one colon, and `displayValue` may preserve uppercase letters. **Requirement context:** Tags exclude Unicode and whitespace, compare case-insensitively, and cannot start or end a component with a hyphen, but exact hyphen count, colon behavior, and display casing are open questions. **Why it matters:** Changing the patterns now could reject valid future input or accept values the product later disallows. **Developer action:** Keep both patterns unchanged until product decisions define the exact grammar and casing policy, then update the patterns and descriptions together.
- **Affected schema item:** `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, fields `status`, `assignedToIdentityId`, `resolvedAt`, `resolvedById`, and `resolutionSummary`. **Current state:** The provisional enum includes `open`, `inReview`, `resolved`, and `closed`, without a defined difference between terminal values or required resolution metadata. **Requirement context:** Tickets must be reviewable and retained, but status, assignment, notification, and closure behavior are explicitly unresolved. **Why it matters:** Different API and UI implementations could close tickets without an outcome or interpret terminal states differently. **Developer action:** Do not add lifecycle conditions until the product owner defines the difference between `resolved` and `closed` and which states require resolution fields.
- **Affected schema item:** `docs/schemas/note.yaml`, object `Note`, field `visibility`. **Current state:** Visibility is optional and accepts `authorOnly`, `moderators`, `owners`, or `participants`, with no default or mutability rule. **Requirement context:** People and moderators may add notes, while note audiences are explicitly unresolved. **Why it matters:** An implicit application default could expose personal or operational notes to unintended readers. **Developer action:** Require a product decision about supported audiences, target-specific defaults, and whether visibility can change before making the field required or defaulting it.
- **Affected schema item:** `docs/schemas/emoji-reaction.yaml`, object `Emoji Reaction`, relationship `(messageId, identityId, emoji)`. **Current state:** The dictionary now checks conversation and active-member authorization, but multiple active matching records or different emojis by one identity remain possible. **Requirement context:** The supported emoji set and whether one identity may add multiple reactions are open questions. **Why it matters:** Premature uniqueness could block intended behavior, while no later uniqueness rule could produce duplicate UI counts. **Developer action:** Decide whether the rule is one total reaction, one per emoji, or multiple retained reactions per message before defining a uniqueness key.
- **Affected schema item:** `docs/schemas/conversation.yaml`, object `Conversation`, fields `purpose`, `visibility`, and `moderationTicketId`; related `docs/schemas/membership.yaml` records. **Current state:** A moderation discussion is now unlisted and ticket-linked, but the general unlisted tag flow can still create Membership without a separate moderator-only access rule. **Requirement context:** The discussion is confidential and behaves like a normal conversation, but whether it is required and who may join are unresolved. **Why it matters:** Unlisted discovery hides identity but does not prevent a person who knows all tags from attempting to join sensitive discussion. **Developer action:** Before implementing the join path, decide whether only owners and administrators of the ticket's source Conversation may join and whether membership must be created by explicit moderator addition.
- **Affected schema item:** `docs/schemas/conversation.yaml`, object `Conversation`, field `status`; relationships to Message, Membership, and Conversation Tag. **Current state:** Archive metadata is internally consistent, but no rule says whether archived conversations are searchable, readable, writable, or joinable. **Requirement context:** Archival replaces hard deletion and retains records, while search and participant-view behavior is explicitly unresolved. **Why it matters:** Client and API paths could disagree, for example allowing new messages through one route while presenting the conversation as read-only elsewhere. **Developer action:** Define archived search, read, write, and join behavior before implementing authorization or adding any further lifecycle fields.
- **Affected schema item:** `docs/schemas/membership.yaml`, object `Membership`, field `currentRole`. **Current state:** `currentRole` is now absent for `left` and `removed` and present only for active or banned memberships. **Requirement context:** Former participants have no current permissions, historical roles remain in Membership Role Period, and `none` means banned. **Why it matters:** A DynamoDB query or response mapper that assumes a scalar role on every record may fail or may accidentally substitute `none`, blurring departure with a ban. **Developer action:** Make authorization require `currentStatus: active`, treat absent role as expected for former non-banned members, and read historical role from Membership Role Period when needed.
