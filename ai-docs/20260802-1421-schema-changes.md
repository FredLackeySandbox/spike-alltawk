# Schema Changes

## Source review

This improvement pass used the exact Agent 1 report `ai-docs/20260802-1413-schema-review.md`. It compared the current `docs/schemas/DICTIONARY.md` and the 17 existing YAML schema files with `docs/concepts/REQUIREMENTS.md`. No YAML schema file was added, removed, or renamed.

In this report, a **foreign key** means an identifier that points to a record in another schema. An **enum** is a field restricted to a fixed list of values. A **lifecycle state** is a named stage such as `active`, `revoked`, or `archived`. **Cardinality** means how many related records may exist, such as one to ten current tags per conversation. A **derived rule** is behavior calculated by comparing records rather than stored in one field. **Normalization** means storing an authoritative fact once and referring to it by identifier rather than copying it into several records.

## Recommendation decisions

| Review ID | Affected schema item | Decision | What changed or why it did not change | Requirement context | Remaining risk |
|---|---|---|---|---|---|
| SR-01 | `docs/schemas/conversation.yaml`, object `Conversation`, fields `purpose`, `accessMode`, `visibility`, and `matchingMode`; `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, field `discussionConversationId` | Accepted | `Conversation.purpose` is now required. New required field `Conversation.accessMode` allows `tagJoin` or `ticketReviewers`. A `general` conversation must use `tagJoin`; a `moderationDiscussion` conversation must use `ticketReviewers`, `unlisted`, and `all`. `docs/schemas/DICTIONARY.md` now states that `ModerationTicket.discussionConversationId` must reference a different, uniquely linked moderation-discussion conversation and that only current owners and administrators of the source conversation are eligible to access it. | Every ticket requires a private discussion. Ordinary listed conversations are discoverable, and ordinary unlisted conversations are joinable by exact tags, so confidentiality requires a distinct access rule that does not grant entry through tags. | A standalone schema cannot prove that `ModerationTicket.discussionConversationId` points to a different conversation or compare reviewer roles. The framework-neutral API/data package must enforce the documented cross-record rule. |
| SR-02 | `docs/schemas/note.yaml`, object `Note`, fields `targetType`, `visibility`, `conversationId`, `threadId`, `messageId`, and `moderationTicketId` | Accepted | Conditional constraints now allow `private` or `conversationParticipants` for conversation notes, `private` or `threadParticipants` for thread notes, and only `moderators` for moderation-ticket notes. Message notes may use the two participant audiences only as candidates; the dictionary requires the application to choose `threadParticipants` when referenced `Message.threadId` is present and `conversationParticipants` otherwise. | Recorded decisions give thread participants a different audience from whole-conversation participants, while operational ticket notes are limited to owners and administrators. | `Note.messageId` and `Message.threadId` are in separate records, so the YAML schema cannot choose the message-note audience by itself. The application must enforce that derived rule. Whether a note's visibility can change later remains unresolved. |
| SR-03 | `docs/schemas/moderation-action.yaml`, object `Moderation Action`, fields `actionType`, `targetIdentityId`, `targetMessageId`, and `postingSuspensionId` | Accepted | The broad target rule was replaced with action-specific branches. Message actions require only `targetMessageId`; participant removal, ban, and unban actions require only `targetIdentityId`; `suspendPosting` requires `targetIdentityId` and `postingSuspensionId`; and `liftPostingSuspension` requires only `postingSuspensionId`. Unrelated target fields are prohibited. The lifted participant remains available through the referenced `PostingSuspension.identityId`, avoiding two potentially conflicting copies. | Owners and administrators can delete messages, change participant access, and create or lift time-limited posting suspensions. The retained action must identify the type of target the named operation actually affects. | Cross-record code must still confirm that every target belongs to `ModerationAction.conversationId` and that the actor has an owner or administrator role at `occurredAt`. |
| SR-04 | `docs/schemas/membership-role-period.yaml`, object `Membership Role Period`, fields `reason`, `startReason`, `effectiveTo`, `endReason`, and `endedById` | Accepted | Former field `reason` was renamed to `startReason`. End-only values `left` and `removed` were removed from the start enum. New `endReason` records `left`, `removed`, `promoted`, `demoted`, `banned`, or `unbanned`. An ended period now requires `effectiveTo`, `endReason`, and `endedById`; a current period prohibits all three ending fields. | Role history must retain promotion, demotion, leaving, removal, banning, and unbanning over time. A start reason alone could not explain why a historical period ended. | Existing persisted records using `reason` will need a bounded data migration before the updated contract is deployed. The schema cannot compare `effectiveTo` with `effectiveFrom`; the dictionary assigns that ordering check to application code. |
| SR-05 | `docs/schemas/conversation-tag.yaml`, object `Conversation Tag`, fields `effectiveTo` and `removedById` | Accepted | An ended tag assignment now requires both `effectiveTo` and `removedById`. A current assignment must omit both. The dictionary retains one-to-ten current assignments as an application/data-access cardinality constraint because one association document cannot count peer records. | Owners and administrators may remove tags, and tag history must be retained with both timing and actor information. | Application code must verify that `effectiveTo` is later than `effectiveFrom`, that the remover is authorized, and that a mutation leaves one to ten current tag assignments. |
| SR-06 | `docs/schemas/membership.yaml`, object `Membership`, fields `status`, `endedAt`, `endedById`, and `endReason` | Accepted | `status: active` now prohibits all ending fields. `left`, `removed`, and `banned` now require `endedAt`, `endedById`, and `endReason`; each status also requires its matching reason value. Earlier cycles remain in `Membership Role Period` and audit history. | Participants may leave and rejoin repeatedly, while removals and bans remain inspectable and the current status controls participation and rejoining. | Application code must coordinate `Membership.status` with the current `MembershipRolePeriod` and prevent a last-owner transition that would leave an active conversation ownerless. |
| SR-07 | `docs/schemas/bot-credential.yaml` fields `status`, `expiresAt`, and `revokedAt`; `docs/schemas/identity.yaml` fields `isActive` and `deactivatedAt`; `docs/schemas/note.yaml` fields `status`, `deletedAt`, and `deletedById`; `docs/schemas/posting-suspension.yaml` fields `liftedAt` and `liftedById` | Accepted | A revoked credential requires `revokedAt`, an expired credential requires `expiresAt`, and an active credential prohibits `revokedAt`. An inactive identity requires `deactivatedAt`, while an active one prohibits it. An active note prohibits deletion fields, while the existing deleted-note rule requires both. A posting suspension now requires `liftedAt` and `liftedById` together or omits both. | Token revocation, identified authentication, soft deletion, and auditable early lifting of suspensions all require internally consistent lifecycle facts. | Cross-record authorization and time ordering remain application responsibilities. In particular, the application must ensure a lift occurs within the suspension interval. |
| SR-08 | `docs/schemas/emoji.yaml`, object `Emoji`, fields `type`, `scope`, `unicodeValue`, `assetUrl`, `assetMediaType`, `ownerIdentityId`, and `conversationId` | Accepted | Three exclusive branches now define valid shapes. A standard emoji has `scope: standard`, requires `unicodeValue`, and prohibits custom asset and ownership fields. An identity-scoped custom emoji requires its asset fields and owner and prohibits `unicodeValue` and `conversationId`. A conversation-scoped custom emoji additionally requires `conversationId` and prohibits `unicodeValue`. | The recorded decision requires a familiar standard emoji set and custom PNG, JPEG, or animated GIF uploads supplied by people or conversation owners. Clients need one unambiguous rendering source. | Custom-emoji upload permissions beyond supplier and conversation scope remain intentionally undefined and must not be inferred from these storage fields. |
| SR-09 | `docs/schemas/DICTIONARY.md`, relationships among `Conversation Tag`, `Membership`, `Membership Role Period`, `Emoji Reaction`, `Moderation Ticket`, and `Conversation` | Accepted | A new `Cross-record integrity rules` section documents composite uniqueness, meaning uniqueness across a combination of fields, for membership, current tag assignments, and active identical reactions; one current role period; at least one active owner; one to ten current tags; globally unique ticket numbers; a one-to-one ticket/discussion relationship; confidentiality of moderation discussions; and required time ordering. | The requirements call for one membership per identity/conversation, one current role, one to ten tags, at least one owner, stable reactions, unique ticket numbers, and one required private discussion per ticket. | These rules cannot be enforced by one standalone JSON Schema document. DynamoDB keys, conditional writes, transactions, or framework-neutral service checks must enforce them without changing their product meaning. |
| SR-10 | `docs/schemas/audit-event.yaml`, object `Audit Event`, fields `createdAt`, `updatedAt`, and `details`; matching `Audit Event` dictionary entry | Accepted | `AuditEvent.updatedAt` was removed from both `required` and `properties`. The append-only record now uses only immutable `createdAt` for persistence time. `AuditEvent.details` and the dictionary now state that the payload is small and non-authoritative and must not copy complete source records. | Retained history must not be silently rewritten, and the requirements do not define a second mutable timestamp for an event. | `AuditEvent.details` still permits action-specific properties because the requirements do not define every event payload. Developers must keep source schemas authoritative and avoid sensitive or complete record copies. |
| OS-01 | `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, field `assignedReviewerId` | Accepted | `assignedReviewerId` was removed. The dictionary states that access is role-based and reviewer assignment is not stored until assignment behavior is decided. | Owners and administrators can review tickets, but reviewer assignment, notifications, and reopening rules are explicitly undefined. | If assignment is later added, its cardinality, reassignment history, and authorization behavior need a new product decision and schema change. |
| OS-02 | `docs/schemas/bot-credential.yaml`, object `Bot Credential`, field `tokenPrefix` | Partially accepted | `tokenPrefix` remains available but is no longer required. Its description and dictionary entry limit it to credential formats that choose prefix-based lookup. `tokenHash` remains required, so raw tokens are still not stored. | Bots authenticate with tokens, while DynamoDB access patterns and credential lookup design remain implementation choices. | A later implementation must decide whether a prefix is needed and, if so, define its format and uniqueness without treating this optional field as an authorization fact. |
| OS-03 | `docs/schemas/audit-event.yaml`, object `Audit Event`, field `details` | Partially accepted | The arbitrary object shape was retained because the requirements do not enumerate event-specific payloads. Its schema description and dictionary entry now restrict its meaning to small, non-authoritative explanation data and prohibit full source-record duplication. | Retained history needs explanations for changes not fully evident from temporal records, but it does not require duplicated authoritative snapshots. | JSON Schema cannot enforce "small" or prove that a payload does not duplicate source data. Code review and event-specific service logic must maintain that boundary. |

## Changed files

- `docs/schemas/conversation.yaml`: `Conversation.purpose` and new `Conversation.accessMode` are required; moderation discussions are confidential, unlisted, all-match records accessed through ticket reviewer roles rather than tag joining.
- `docs/schemas/note.yaml`: `Note.visibility` is constrained by `Note.targetType`, and `Note.status: active` prohibits `deletedAt` and `deletedById`.
- `docs/schemas/moderation-action.yaml`: `ModerationAction.actionType` now determines the exact allowed target fields.
- `docs/schemas/membership-role-period.yaml`: `MembershipRolePeriod.reason` became `startReason`; new `endReason` and paired ending-field rules preserve why each role period ended.
- `docs/schemas/conversation-tag.yaml`: `ConversationTag.effectiveTo` and `removedById` must be present or absent together.
- `docs/schemas/membership.yaml`: Active membership ending fields are prohibited; inactive states require an actor, timestamp, and matching reason.
- `docs/schemas/bot-credential.yaml`: `BotCredential.tokenPrefix` is optional, and `status` now controls required or prohibited lifecycle timestamps.
- `docs/schemas/identity.yaml`: `Identity.isActive` now controls whether `deactivatedAt` is required or prohibited.
- `docs/schemas/posting-suspension.yaml`: `PostingSuspension.liftedAt` and `liftedById` must appear together.
- `docs/schemas/emoji.yaml`: `Emoji.type` and `scope` now select one valid standard, identity-custom, or conversation-custom field set.
- `docs/schemas/moderation-ticket.yaml`: Speculative `ModerationTicket.assignedReviewerId` was removed while role-based review access remains unchanged.
- `docs/schemas/audit-event.yaml`: Append-only `AuditEvent.updatedAt` was removed, and `details` is explicitly non-authoritative.
- `docs/schemas/DICTIONARY.md`: Object entries were updated to match the changed fields and a cross-record integrity section now documents rules that individual YAML schemas cannot express.

## Rejection and partial-acceptance rationale

No SR-* recommendation was rejected. Each one corrected a concrete contradiction or integrity gap already grounded in the requirements.

- OS-02 was only partially accepted because removing `BotCredential.tokenPrefix` entirely would forbid an implementation from using a harmless non-secret lookup hint. Making it optional avoids committing the product schema to that strategy while preserving the field for a selected credential format.
- OS-03 was only partially accepted because the requirements do not define a closed set of `AuditEvent.action` names or corresponding detail fields. Replacing `AuditEvent.details` with a guessed fixed structure would be speculative. The schema and dictionary now set the safe semantic boundary without inventing event payloads.

## Remaining known risks

- `docs/schemas/message.yaml`, object `Message`, fields `status` and `hiddenByTicketId`; `docs/schemas/message-thread.yaml`, object `Message Thread`, fields `status` and `pausedByTicketId`; and `docs/schemas/moderation-ticket.yaml`, object `Moderation Ticket`, field `status` do not define what happens when review ends without message deletion. A closed ticket could otherwise leave a message hidden or a thread paused. This needs a product decision, so no lifecycle value was invented here.
- `docs/schemas/tag.yaml`, object `Tag`, field `value` has no numeric maximum length because `docs/concepts/REQUIREMENTS.md` refers to a component maximum without choosing one. Clients and APIs must not invent different limits; a product decision is still needed.
- `docs/schemas/identity.yaml`, object `Identity`, field `email`, and `docs/schemas/human-authentication.yaml`, object `Human Authentication`, field `email` can disagree because the requirements do not define how a canonical profile email relates to multiple sign-in connections. Account linking and lookup code must not silently assume every provider returns the same address.
- `docs/schemas/message.yaml` field `hiddenByTicketId`, `docs/schemas/message-thread.yaml` field `pausedByTicketId`, and `docs/schemas/moderation-ticket.yaml` field `messageId` still leave the number of simultaneous open tickets per message unresolved. Code must not overwrite one ticket link with another until the product chooses one-open-ticket or multi-ticket behavior.
- `docs/schemas/audit-event.yaml`, object `Audit Event`, field `details` remains structurally open. Developers must follow its non-authoritative contract and avoid copying complete profile, message, or moderation records into the payload.
