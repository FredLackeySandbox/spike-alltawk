Convert every approved desktop mockup page into a faithful interactive v0 page
with a deliberately tiny, fixture-backed mock API client.

This is a responsibility-separation task, not a rewrite and not a domain
simulation. Preserve all existing visible functionality, but keep presentation,
browser behavior, and interaction state in the HTML page.

## Definition of "fully functional"

"Fully functional" means that every interaction already implemented by the source
page still works and produces the same visible result. It does not mean that the
mock API must implement a real backend, domain model, database, state machine, or
application architecture.

The output has this strict ownership boundary:

| File | Owns | Must not own |
| --- | --- | --- |
| `{page}.html` | DOM queries and updates, rendering, event handlers, keyboard behavior, validation messages, loading indicators, modal/menu behavior, navigation, timers, UI state, and orchestration of API calls | Mock response payloads that belong in the fixture |
| `{page}-api.js` | Loading the fixture and exposing small API-shaped functions that return fixture values | DOM access, rendering, event handling, validation, permissions, business rules, workflow/state machines, navigation, timers, or realistic persistence |
| `{page}-data.json` | Small deterministic values returned by the mock API | UI state, presentation instructions, scenario engines, normalized database tables, schema mirrors, audit history, or fields unused by an API return value |

When ownership is unclear, keep the logic in the HTML. The API file is intentionally
boring.

## Scope

Recursively find every `.html` page beneath `docs/mockup/desktop/`. Shared assets
and non-HTML files are not pages.

For each source page, mirror its relative path beneath
`docs/mockup/desktop-v0/` and create exactly:

- `{page}.html`
- `{page}-api.js`
- `{page}-data.json`

Do not modify source mockups, shared assets, schemas, or concept documents. Do not
create other implementation files.

## Agents

The primary agent is an orchestrator only. It must first inventory the complete set
of source HTML paths without reading or analyzing page contents. It must not
implement or edit files, run page tests, or validate results. It may only manage
page assignments, enforce this workflow, relay essential context, and report the
final outcome.

After the inventory is complete, create one isolated two-agent workstream for every
discovered page. Each pair owns only its page's three output files and must not
inspect or change another page's outputs. Use these agents in order within each
pair:

1. **Page Implementation Agent**

   Analyze the assigned source page, create its three output files, run every
   required test, fix failures, retest, and hand off the files and test results.

2. **Page Verification Agent**

   Start only after that page's Implementation Agent finishes. Independently
   compare the source and outputs, rerun every test, and directly correct defects.
   The verifier must reject unnecessary abstraction, DOM code in the API, business
   logic in the API, schema-shaped fixture bloat, and duplicated presentation data.
   It should simplify or delete excess code, not merely confirm behavior. Return
   `APPROVED` only when behavior and separation both pass; otherwise return
   `BLOCKED` with specific evidence.

The Verification Agent owns final quality for its page and must not send
corrections back to the Implementation Agent. Different page pairs may run in
parallel as capacity allows, but the Implementation -> Verification order is
mandatory within every pair. Assign exactly one pair per page and use no other
agents.

## Analyze the source

Both agents in a page pair must independently read the entire assigned source page
and its directly referenced local CSS and JavaScript.

Inventory the source page's existing visible states and interactions. For each
interaction, decide whether a real application would contact a backend.

- If no backend call would be made, keep the interaction entirely in the HTML.
- If a backend call would be made, keep the event handler, validation, loading
  state, rendering, DOM update, timing, navigation, and error presentation in the
  HTML. Add one call from that HTML logic to a small function in `{page}-api.js`.
- Do not create one API function for every click, keypress, modal, or state change.
  Create a function only for a backend-shaped operation such as loading, creating,
  updating, deleting, or submitting data.

### Mandatory interaction-state coverage

Before editing any output file, use browser automation against the source page to
build an interaction-state matrix. Static source inspection alone is insufficient.

A state is any visually or semantically distinct page condition supported by the
source markup, CSS, JavaScript, URL or query handling, or enabled controls. Include:

- the initial, loading, loaded, empty, failure, denied, and recovery states;
- every tab, segmented-control, radio-group, and toggle selection;
- every `<select>` option that produces distinct content, enabled state, validation,
  request, or navigation;
- the open and closed states of menus, disclosures, popovers, and dialogs;
- every distinct menu command, including cancel and confirm outcomes;
- validation states and dependent-field changes;
- disabled, busy, success, and failure states for submitted actions;
- URL, query-string, hash, and source-defined QA or fixture variants;
- state changes caused by repeated actions and multi-step action sequences; and
- the keyboard path and focus result for interactive components.

For each state, record this matrix in the agent handoff:

| State ID | Entry action or URL | Source evidence | Expected visible and accessibility result | Exit or recovery action | Tested |
| --- | --- | --- | --- | --- | --- |

Do not create a separate matrix file. Include it in the agent's handoff and final
verification report.

Every matrix row and every transition between rows must be reproduced and tested
in the output. A page may not be approved from an initial-view comparison alone.

Do not invent behavior based only on a control's label. If a visible control implies
a state but the source provides no corresponding markup, script, target page, or
other behavioral evidence, report it as a source-contract limitation rather than
silently implementing or ignoring it.

Use schemas only when needed to confirm the name or shape of a value that the page
actually receives from an API call. Do not copy schema entities, relationships,
history records, metadata, or invariants into the fixture.

## HTML requirements

Start from a copy of the complete source page.

- Preserve its content, markup, rendering, accessibility, responsive behavior,
  initial state, interactions, and state transitions.
- Preserve its page-specific JavaScript in the HTML. Do not relocate existing UI
  functions into the API file.
- The HTML must continue to own every `addEventListener`, DOM query and update,
  validation branch, modal/menu transition, focus operation, timer, and navigation.
- Replace only the small portions that pretend to be backend calls or contain
  hard-coded backend response values. Call the sibling API function at those
  points, then let the HTML render the returned value.
- Presentation strings, labels, CSS classes, selectors, element IDs, button state,
  and QA/demo controls remain in the HTML and must not be copied into JSON.
- Load `{page}-api.js` before the page-specific script uses it. The HTML explicitly
  calls the API's fixture initializer; the API must not initialize the page or bind
  handlers itself.
- Reuse source shared assets read-only, adjusting relative paths only as required.
- Link to a matching v0 page when one exists; otherwise preserve the source target.
- Add no framework, build step, remote dependency, or external service.

## Mock API requirements

Create a browser-compatible mock of the client library that a real page would
call. It is not a mock backend implementation.

The API file may do only these things:

- fetch `{page}-data.json` once in a small `init...` function;
- retain the parsed fixture in one private variable;
- expose plainly named functions such as `getSomething`, `createSomething`,
  `updateSomething`, `deleteSomething`, or `doSomething`;
- accept an object parameter that shows the intended request contract;
- select an already prepared fixture value by a direct property or array lookup;
- return that value, preferably as a defensive copy or resolved Promise; and
- export one page-specific namespace on `window`.

The API file must not:

- access `document`, elements, selectors, classes, attributes, styles, or focus;
- register or dispatch events;
- render strings or HTML;
- display validation, loading, empty, success, failure, menu, or modal states;
- navigate, reload, inspect URL query parameters, or read browser storage;
- use timers to simulate latency;
- contain permission checks, validation rules, sorting, filtering, joining,
  aggregation, record assembly, workflow branching, or other business logic;
- create a normalized in-memory domain model or mutate related records;
- generate IDs, timestamps, audit records, role periods, or history;
- implement duplicate-submission protection or other UI coordination;
- expose page initialization, render, bind, modal, toast, or navigation functions;
  or
- add abstractions, classes, repositories, services, stores, event buses, or helper
  layers. Apart from fixture loading and optional defensive copying, helpers are
  unnecessary.

Each public function should normally contain one fixture lookup and one return.
Parameters may be unused only when they do not affect the source page's observable
result. When a tab, filter, dropdown, pagination control, or other selection causes
a backend-shaped request with a distinct response, the fixture must contain one
small prepared response per distinct request value, and the API must select it by
a direct parameter-key lookup. This lookup is permitted and is not business logic.
Immediately above each function, use a short comment to describe what a real backend
would do. Do not implement those comment steps in the mock.

Use this shape as the model:

```js
(function () {
  "use strict";

  let data;

  async function initWidgetApi() {
    const response = await fetch("widget-data.json");
    data = await response.json();
  }

  async function doSomething({ valueA, valueB }) {
    // Real backend responsibility:
    // 1. Look up X.
    // 2. Find matching Y records.
    // 3. Assemble the response where A equals B.
    return structuredClone(data.things.widgetArray);
  }

  window.WidgetApi = { initWidgetApi, doSomething };
})();
```

Do not add logic to `doSomething` merely because its parameters are present.

For a request parameter that selects among distinct prepared responses, use this
shape instead:

```js
async function getRoster({ membershipState }) {
  // A real backend would authorize the request and query the roster.
  return structuredClone(data.rostersByMembershipState[membershipState]);
}
```

## Fixture requirements

Create valid, deterministic JSON containing only values directly returned by the
mock API functions. Prefer compact, denormalized, screen-level response objects.

Use this shape as the model:

```json
{
  "things": {
    "widgetArray": [
      {
        "id": "abc123",
        "name": "Something"
      }
    ]
  }
}
```

- Include only fields that the HTML reads from an API result.
- Use the fewest records needed to preserve the source page's behavior.
- Store a final mock response directly instead of storing normalized input records
  and assembling them in JavaScript.
- Do not reproduce complete schema entities just because a schema defines them.
- Do not add `scenario`, `presentation`, `simulation`, delay, selector, CSS class,
  DOM ID, copy, relationship, or audit metadata unless that exact value is part of
  a response visibly consumed by the page.
- Do not duplicate static content that remains in the HTML.

## Simplicity guardrails

These are rejection thresholds, not targets:

- `{page}-api.js` must be no more than 200 physical lines, including comments and
  blank lines.
- `{page}-data.json` must be no more than 200 physical lines.
- A public API function must be no more than 12 physical lines, including its
  backend-responsibility comment.
- The API may have only the fixture variable plus two generic private helpers:
  fixture loading and defensive copying.
- Keep readable formatting; do not minify or compress code to satisfy a limit.

If faithful behavior appears to require exceeding a limit, first move UI logic
back into the HTML and replace computed domain data with a prepared fixture
response. If a limit still cannot be met, return `BLOCKED` and explain the exact
need. Do not silently exceed it.

## Test

Serve the source and output through a local HTTP server and use browser automation.
Both agents in every page pair must independently:

1. Compare source and output at two representative desktop viewport sizes.
2. Confirm visual parity for the initial view and every source-defined visible
   state.
3. Exercise every source-defined interaction, keyboard path, validation path,
   repeated action, recovery path, and navigation; observable results must match.
4. Confirm that calls which represent backend operations pass through the mock API
   and return fixture values.
5. Confirm reload resets the page and repeated UI actions retain the source
   behavior.
6. Confirm there are no missing resources, JavaScript errors, unhandled
   rejections, unexpected console errors, or external requests.
7. Inspect `{page}-api.js` and fail verification if it contains `document`,
   `querySelector`, `addEventListener`, `classList`, `innerHTML`, `textContent`,
   `location`, `localStorage`, `sessionStorage`, or `setTimeout`.
8. Confirm the API and JSON are within all simplicity guardrails.
9. Confirm they changed only their assigned page's three output files.
10. Compare the implementation and verification state matrices. The verifier must
    independently rediscover the states rather than relying only on the implementer's
    inventory.
11. Activate every tab, segmented-control choice, radio choice, and behaviorally
    distinct select option in both source and output.
12. After every activation, compare visible content, visibility, selected or pressed
    attributes, disabled state, focus, live-region output, and URL changes.
13. Exercise every source-defined query, hash, fixture, or QA variant found in the
    source JavaScript.
14. Record the number of discovered states, transitions, and covered states. Approval
    requires 100% coverage; undocumented sampling is not sufficient.

Visual and behavioral parity alone is not sufficient. Any separation violation,
unnecessary fixture field, unnecessary helper, or guardrail violation is a failed
check and must be corrected and retested.

## Report

After every page is approved, the orchestrator reports:

- the number of pages discovered and approved;
- each source page and its three output paths;
- each page's API namespace and functions;
- the line counts of each API and JSON file;
- confirmation that all UI logic remained in the HTML;
- the behaviors and checks completed for each page;
- each page's interaction-state matrix and its discovered-state, transition, and
  covered-state counts; and
- any contract limitation.

The task is complete only when every source page has exactly one approved output
set, all required files exist, behavior matches the source, the API files are thin
fixture facades, the JSON files are compact response fixtures, and every test
passes.
