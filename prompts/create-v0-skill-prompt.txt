Convert one approved desktop mockup page into a faithful, fully functional v0
page.

## Scope

`SOURCE_PAGE` must identify one HTML file beneath `docs/mockup/desktop/`. If it
does not, request one exact path.

Mirror its relative path beneath `docs/mockup/desktop-v0/` and create exactly:

- `{page}.html`
- `{page}-api.js`
- `{page}-data.json`

Do not modify source mockups, shared assets, schemas, or concept documents. Do not
create other implementation files.

## Agents

The primary agent is an orchestrator only. It must not inspect project files,
analyze the page, implement or edit files, run commands or tests, or validate the
result. It may only launch the two agents below, pass them this prompt and
`SOURCE_PAGE`, enforce their sequence, relay essential context, and report the
final outcome.

1. **Implementation Agent**

   Analyze the source, create all three output files, run every required test, fix
   failures, retest, and hand off the files and test results.

2. **Verification Agent**

   Start only after the Implementation Agent finishes. Independently analyze the
   source and contracts, inspect the outputs, and rerun every test. Directly correct
   all defects, omissions, and missing functionality in the three output files,
   then retest. Return `APPROVED` only when everything passes; otherwise return
   `BLOCKED` with specific evidence.

The Verification Agent owns final quality and must not send corrections back to the
Implementation Agent. Do not use any other agent.

## Analyze and implement

Each agent must independently read the entire source page, its local CSS and
JavaScript dependencies, and only the relevant schemas. Identify:

- all initial data and rendered values;
- every implemented action, event, keyboard behavior, and navigation;
- every loading, empty, success, validation, error, disabled, menu, and modal state;
- inputs, results, mutations, permissions, filters, sorting, selection, and derived
  values; and
- controls that are functional, decorative, explanatory, or browser-native.

Map each implemented behavior as:

`event -> API function -> data read or mutation -> result -> DOM update or navigation`

The source is the visual and behavioral specification. Reproduce only what exists.
Do not add, remove, redesign, reinterpret, or simplify visible functionality.

### HTML

Start from a copy of the source page.

- Preserve its content, rendering, accessibility, responsive behavior, initial
  state, interactions, and state transitions.
- Move page-specific data and behavior into the sibling API and data files.
- Load `{page}-api.js` and initialize it after the DOM is ready.
- Add only non-rendering `data-*` hooks when necessary.
- Reuse source shared assets read-only, adjusting relative paths only as required.
- Link to a matching v0 page when one exists; otherwise preserve the source target.
- Add no framework, build step, remote dependency, or external service.

### API

Create working browser-compatible JavaScript, not stubs.

- Expose a page-specific namespace with functions for initialization and every
  data-backed source behavior.
- Load `{page}-data.json`; keep backend-like operations asynchronous and mutations
  in page-local memory.
- Preserve validation, branching, timing, side effects, DOM results, and
  repeated-action behavior.
- Prevent duplicate initialization, bindings, records, and submissions.
- Use defensive copies and deterministic fixture values. Do not use randomness,
  current-time values, hidden persistence, or real network calls.
- Add concise JSDoc to exposed functions and comments only where logic is not
  obvious.

Decorative controls must remain decorative.

### Data

Create deterministic, valid JSON containing only data needed for existing page
states and behavior. Preserve approved names, types, enums, relationships, and
invariants. Do not change schemas or add convenience fields to domain objects.
Keep presentation copy and scenario metadata outside domain records.

## Test

Serve the source and output through a local HTTP server and use browser automation.
Both agents must independently:

1. Compare source and output at two representative desktop viewport sizes.
2. Confirm visual parity for the initial view and every source-defined visible
   state.
3. Exercise every source-defined interaction, keyboard path, validation path,
   repeated action, recovery path, and navigation; observable results must match.
4. Parse the fixture and validate relevant records, relationships, and invariants.
5. Confirm reload resets the scenario and repeated initialization creates no
   duplicate effects.
6. Confirm there are no missing resources, JavaScript errors, unhandled rejections,
   unexpected console errors, or external requests.
7. Confirm only the three required output files changed.

Any difference, omission, error, or failed check must be corrected and retested.

## Report

After approval, the orchestrator reports the source and output paths, API namespace
and functions, behaviors tested, verification results, and any contract limitation.

The task is complete only when the Verification Agent approves a fully functional,
faithful representation of `SOURCE_PAGE` with every test passing.
